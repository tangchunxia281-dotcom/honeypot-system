# 模型优化清单

> 基于当前模型（v2，训练于 2026-10-20）的实际错误样本分析
> 评估数据：独立测试集 7922 条（未参与训练）

---

## 零、跨数据集实验结论（2026-10-20 实测，重要）

为验证"换一批数据还能不能认对"，跑了跨数据集实验（只比较双方共有的
`xss`/`sqli`/`path_traversal`/`normal` 四类）：

### 0.1 两个方向的结果差异极大

| 实验 | 准确率 | 宏 F1 | 攻击识别率 | 攻击精确率 |
|---|---|---|---|---|
| 对照组：原始数据 80/20（同分布） | 99.11% | 0.9395 | 96.22% | 98.59% |
| **A. payload 训练 → 原始数据测** | **55.59%** | 0.6393 | 88.19% | **26.37%** |
| **B. 原始数据训练 → payload 测** | 94.15% | 0.8272 | 92.01% | **92.82%** |

**A 方向崩了**：准确率 99.11% → 55.59%，normal 识别率仅 **48.40%**，
即**超过一半的正常访问会被误判成攻击**。

### 0.2 根因定位：不是攻击数据的问题，是 `normal` 样本的性质问题

payload 数据集的 19,304 条 `normal` 是**西方人名、地址、证件号、邮箱**：

```
'24575080v'                  ← 证件号
'palazuelos de eresma'       ← 地名
'plaza de san isidro 45,'    ← 地址
'brinton2@tartasconamor.lr'  ← 邮箱
```

而蜜罐真实流量是 **URL 路径、HTML 内容、查询参数**：

```
/search?q=hello    /api/v1/users    /index.php?page=2    /.well-known/
```

统计：payload 的 `normal` 里**含斜杠（像路径）的只有 683 条（3.5%）**。

### 0.3 对照实验：normal 样本该用哪种

固定攻击样本，只改 `normal` 来源，用**完全独立的 Web 流量**
（正常路径 128 条 + 正常 HTML 54 条，从不参与训练）测试：

| normal 来源 | 训练 normal 数 | Web 流量准确率 | 误判为攻击 |
|---|---|---|---|
| **① 只用原始数据的 normal** | 5,610 | **94.51%** | **10 条** |
| ② 只用 payload 的 normal | 19,302 | 76.92% | 42 条 |
| ③ **两者全用（当前做法）** | 24,912 | 87.91% | **22 条** |

**结论**：

1. payload 的 `normal` **对 Web 流量有害**——它教模型"地址/证件号是正常"，
   却没有教"URL 路径是正常"
2. **当前模型（做法③）在独立 Web 流量上是 87.91%**，而只用原始 normal 能到 **94.51%**
3. 也就是说：**丢掉 payload 的 19,302 条 normal，误报能从 22 条降到 10 条**

### 0.4 已执行的调整与效果

根据上述实验，已执行以下调整：

| 调整 | 说明 |
|---|---|
| **丢弃 payload 的 19,302 条 `normal`** | 表单数据与 Web 流量不同质 |
| 保留 payload 全部攻击样本 | sqli 10,848 / xss 532 / path_traversal 288 |
| 补充 105 条数字型正常样本 | 修复剔除后纯数字被误判为 SQLi 的问题 |
| 保留正常路径语料 128 条 + 正常 HTML 语料 54 条 | 教模型"URL 路径和网页代码是正常的" |

**效果对比**（独立 Web 流量测试）：

| 指标 | 调整前 | 调整后 |
|---|---|---|
| 训练集 `normal` 含斜杠比例 | 16.3% | **49.8%** |
| 独立 Web 流量准确率 | 87.91% | **100%**（47 条典型请求，0 误报） |
| `normal` 类识别率 | 87.9% | **99.31%** |
| 交叉验证宏 F1 | 0.9959 | **0.9900**（数据量减半但更真实） |

**注意**：训练样本从 119,606 降至 104,309，但**数据质量提升**。
交叉验证宏 F1 略降（0.9959 → 0.9900）是因为数据变少，
但**在真实 Web 流量上的误报从 12% 降到 0%**——这才是部署时关心的。

### 0.5 不需要"另外找很多 normal"

方向比数量重要。当前 5,822 条 `normal` 已够用：

| normal 来源 | 条数 | 作用 |
|---|---|---|
| 原始基准数据 | 5,610 | 主要基础（含大量网页/文本内容） |
| 正常路径语料 | 128 | 教模型"URL 路径是正常的" |
| 正常 HTML 语料 | 54 | 教模型"网页代码是正常的" |
| 数字型语料 | 105 | 教模型"ID/编号是正常的" |

**结论**：不需要找几万条 normal，**用蜜罐真实流量补 500~1000 条效果最好**——
因为蜜罐流量才是最终要面对的数据分布。

## 二、错误样本分析（优化依据）

### 2.1 漏报 19 条，全部是 SQLi / XSS 的"裸片段"

| 样本 | 模型攻击概率 | 问题 |
|---|---|---|
| `create user name identified by 'pass123'` | 0.045 | 合法 SQL 语句，无注入符号 |
| `truncate` | 0.015 | 单个 SQL 关键字 |
| `PRINT @@variable` | 0.236 | SQL Server 语法片段 |
| `or 2 > 1` | 0.366 | 恒真条件但形态不典型 |
| `(1589=1589)*1` | 0.271 | 数值恒真表达式 |
| `exec sp_addlogin 'name' , 'password'` | 0.548 | 存储过程调用 |
| `order by` | 0.695 | 正常 SQL 也会用（歧义） |
| `iif(1539=1539,1539,1/0)` | 0.704 | SQL Server 函数 |
| `<math><mtext></mtext></math>` | 0.382 | XSS 边缘载荷 |
| `<embed src="data:image/svg+xml;base64,...">` | 0.225 | SVG 编码载荷 |
| `<?import namespace="t" ...>` | 0.136 | 旧版 IE XSS |

**共同特征**：都是**脱离上下文的 SQL/XSS 语法片段**，人工也很难判断是不是攻击
（`order by`、`truncate` 本身是合法 SQL）。

### 2.2 误报 2 条，都是"合法的 `<script>` 标签"

| 样本 | 原因 |
|---|---|
| `<script src="https://cdn.example.com/app.js"></script>` | 引外部 JS 的正常写法 |
| `<script src="_static/doctools.js"></script>` | Sphinx 文档页固有标签 |

**根本矛盾**：`<script>` 标签**本身无法区分攻击与正常**，必须看标签内的内容
（`<script>alert(1)</script>` 是攻击，`<script src=...>` 是正常）。

## 三、优化清单（按优先级）

### P0 — 必须先做（影响结论可信度）

| # | 问题 | 现状 | 建议做法 | 预期收益 |
|---|---|---|---|---|
| 1 | **无跨数据集验证** | 所有指标都来自我们自己划分的测试集（同分布），**可能高估** | 找 1-2 个公开数据集（如 PayloadsAllTheThings、SecLists）做独立测试 | 拿到真实的泛化能力，避免自评虚高 |
| 2 | **`normal` 样本非真实流量** | 现有 normal 多为姓名/地址/数字（来自 payload 数据集）+ 手工构造的路径 | 用**蜜罐真实正常流量**（`honeypot_events.jsonl` 里 is_attack=false 的样本）替换或补充 | 直接降低线上误报 |
| 3 | **`scanner` 类模型未训练** | 模型只有 5 类，扫描器 100% 靠规则；规则失效时无兜底 | 给模型增加 `scanner` 类（需采集 UA 样本） | 扫描器识别不再单点依赖规则 |

### P1 — 效果提升明显

| # | 问题 | 现状 | 建议做法 | 预期收益 |
|---|---|---|---|---|
| 4 | **`xss` 是最弱的一类** | 识别率 98.00%、精确率 98.99%（其余类均 ≥99%） | ① 补 XSS 载荷（尤其 SVG/data URI/旧 IE）；② 补正常 `<script>` 用法；③ 增加"HTML 上下文"特征 | xss 识别率可望到 99%+ |
| 5 | **线性模型学不了特征组合** | 字符 TF-IDF + 逻辑回归，无法表达"`<` 且 `onerror` 且 `alert`"这类组合 | 试 **LightGBM / 随机森林**（保留字符 n-gram 特征） | 组合特征类误报可降；代价是失去部分可解释性 |
| 6 | **模型文件偏大** | 160,808 维特征、9 MB 模型（`min_df=1`） | 调 `min_df=2~3` 或 `max_features=50000` | 模型可压到 2-3 MB，推理更快 |
| 7 | **敏感路径类别样本仍少** | 训练集 194 条（测试 49 条） | 补充 `/root/.ssh/`、`/var/log/` 等系统路径族 | 该类稳定性提升 |

### P2 — 进阶优化

| # | 问题 | 建议做法 | 说明 |
|---|---|---|---|
| 8 | **双阈值未调优** | 在验证集上绘制 PR 曲线，找最优的 `SUSPICIOUS_THRESHOLD` | 当前固定 20，未做数据驱动选择 |
| 9 | **未利用 HTTP 上下文** | 把 `method`、`Content-Type`、参数名、请求频率作为额外特征 | 目前只吃文本，`%00`、超长参数等信号浪费了 |
| 10 | **无在线学习机制** | 人工确认的误报/漏报样本自动进入待训练队列 | 现在靠手工维护 `extra_samples.csv` |
| 11 | **未做对抗性测试** | 对已知绕过手法（双重编码、注释混淆、Unicode）系统测试 | 现有归一化只做 URL/HTML 实体/`\uXXXX` 解码 |

## 四、优先做什么（建议顺序）

如果时间有限，按这个顺序做性价比最高：

```
① 用蜜罐真实 normal 流量替换训练集里的合成 normal   ← 收益最大、成本最低
② 找公开数据集做跨集验证                          ← 验证是否自评虚高
③ 补 XSS 样本（最弱类）
④ 给模型加 scanner 类
⑤ 调 min_df 压缩模型
⑥ 试 LightGBM（可选，需权衡可解释性）
```

**理由**：①② 直接决定"这个 99.7% 可不可信"；③ 补最弱环节；
④ 消除对规则的硬依赖；⑤⑥ 是工程优化，收益递减。

## 五、已知的能力边界（需向上汇报）

| 能做到 | 做不到 |
|---|---|
| 5 类攻击判定 + 类型细分 | 命令注入（cmdi）、SSRF、XXE、CSRF |
| 输出加权分值（`ai_points` 0~25） | 独立做最终判定（需蜜罐双阈值累加） |
| 对规则未覆盖的变体有泛化能力 | 判断脱离上下文的 SQL 片段（如 `order by`） |
| 弱信号叠加（敏感路径 + AI → 过告警线） | 识别扫描器（模型未训练该类） |

**核心局限**：模型是**文本级**的，只看字符串内容，
不理解该字符串出现在什么上下文（URL 参数 / HTML 正文 / SQL 语句）。
P2-9 的"利用 HTTP 上下文"是突破这个局限的方向。
