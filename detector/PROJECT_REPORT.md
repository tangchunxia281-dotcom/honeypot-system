# XSS Detector —— 数据治理与模型优化报告

**项目**：Web 攻击检测 AI 辅助分析层（对接蜜罐"多特征加权 + 双阈值分层"机制）
**报告日期**：2026-10-14
**评估方式**：5 折分层交叉验证（39608 条清洗后样本，每类均出现在每折验证集中）

---

## 一、项目定位

本模块是为蜜罐系统提供**一维 AI 加权特征**与**攻击类型细分**的独立服务，
通过 HTTP 接口与蜜罐解耦对接：

```
┌──────────────────┐   POST /api/v1/detect   ┌────────────────────┐
│ 蜜罐模块          │ ──────────────────────> │ AI 检测服务（本模块）│
│ Web/SSH 采集+存储 │ <────────────────────── │ 规则引擎 + 机器学习  │
└──────────────────┘   判定结果 + 分值        └────────────────────┘
```

- **输入**：蜜罐采集的 HTTP 请求（path / query / body / headers / User-Agent）
- **输出**：攻击类型、攻击概率、建议累加分值（`ai_points`，0~25）、可读理由、命中证据
- **不做封禁决策**，只输出判定与分值，最终处置由蜜罐决定

| 判定类型 | 含义 |
|---|---|
| `xss` | 跨站脚本 |
| `sqli` | SQL 注入 |
| `path_traversal` | 目录穿越（含 `../`） |
| `sensitive_path` | 敏感文件/目录探测（不含 `../`） |
| `scanner` | 自动化扫描器指纹 |
| `normal` | 正常流量 |

## 二、核心工作：数据治理

前期的数据存在系统性问题，**原有指标不可信**。主要发现与处置如下。

### 2.1 `path_traversal` 标签把两类攻击混在一起（最严重）

标注为"路径遍历"的样本中，**59% 不含任何遍历特征**：

```
原始备份:  69/117 (59.0%) 不含路径遍历特征
训练集  :  32/62  (51.6%)
测试集  :  13/16  (81.2%)
```

这些"误标"样本实际是：`/admin/`、`/phpmyadmin/`、`/console`、`/config.php`、`/.git/config`……

**根本原因：两类语义不同的行为被合成了一个标签**

| 类别 | 典型样本 | 检测逻辑 |
|---|---|---|
| 真正的目录穿越 | `../../etc/passwd`、`..%2f..%2f` | 找 `../` 序列及编码变形 |
| 敏感文件/目录探测 | `/wp-config.php`、`/.env`、`/phpmyadmin` | 找敏感文件名、目录字典 |

**处置**：拆分为 `path_traversal`（20 条真穿越）与 `sensitive_path`（93 条敏感路径）两类。
该拆分也与蜜罐权重表一致——路径探测 +15、目录穿越/LFI +22。

### 2.2 `sqli` 类混入约 10% 的碎片噪声

```
base64 分片残留 : 'UEf'  'UEv'  'UEs'  '{s'
函数名被拆开    : 'left'  'count'  'having'  'user()'
单字符/符号     : 'v'  'c'  '@'  '?'  '%28'  '//'
```

这些是数据转换时被错误切分的残留，模型无法从中学习有效模式。
**处置**：剔除 70 条碎片噪声，并输出 `dropped_samples.csv` 供人工复核。

### 2.3 训练集 `normal` 类缺少 WEB 路径样本（会导致系统性误报）

发现一个**对蜜罐场景致命**的问题：

| 类别 | 样本长度均值 | 训练样本数 | 路径型样本 |
|---|---|---|---|
| `normal` | 174 字符 | 5610 | **仅 18 条** |
| `sensitive_path` | 14 字符 | 74 | 几乎全部 |

模型在"短路径"这个输入域上**只见过攻击样本**，因此把任何短路径都判成敏感文件：

```
'/'           → sensitive_path   攻击概率 1.000   ← 正常首页
'/index.php'  → sensitive_path   攻击概率 0.989   ← 正常文件
```

蜜罐收到的真实流量**几乎全是路径**，这会造成大量误报。

**处置**：
1. 补充 128 条正常 Web 路径语料（`data/raw/extra_benign_paths.csv`）
2. 增加"已知安全路径白名单"机制（`src/rules.py::BENIGN_PATHS`），命中时扣减 20 分
3. 修正数据增强逻辑——原逻辑为每条敏感路径拼接 `/index.php`，
   产生 `/.git/config/index.php` 这类无意义变体，反而强化了错误模式

**验证结果：38 条常见正常路径（`/`、`/index.php`、`/api/users`、`/static/css/style.css` 等）误报 0 条。**

### 2.4 其他清理项

| 问题 | 处置 |
|---|---|
| 混入 1 行重复表头脏行（`source=source`, `label=label`） | 删除 |
| 训练集与测试集有 1 条文本重叠 | 重新生成划分 |
| 模型元数据与实际数据不符（meta 4383 vs 实际 13091） | 重新训练并同步元数据 |
| 增强集把攻击类放大到 72.6%，但 normal 未增强 | 训练/测试分布不一致，已调整 |

## 三、规则引擎改进

| 项 | 改进前 | 改进后 |
|---|---|---|
| 规则总数 | 60 | **166** |
| 规则类别 | 3 类 | **5 类**（新增 `sensitive_path`、`scanner`） |
| sqli 规则 | 17 | **46** |
| sensitive_path 规则 | — | 60 |
| scanner 规则 | **0** | 21 |

**重点补充：**

1. **SQLi 形态**：`group by ... having`、`user()`/`database()`/`version()`、
   报错注入 `extractvalue`/`updatexml`/`exp(~)`、盲注函数、`case when`、`if(...)`、
   十六进制绕过等
2. **扫描器指纹**：原系统**完全没有**扫描器识别规则，
   现补充 sqlmap / nikto / nmap / nuclei / gobuster / awvs 等 21 条
3. **规则误报修正**：裸关键字规则会在普通单词内部误匹配，
   例如 `\bor\b` 会命中 `.DS_Store` 里的 "or"，导致把文件名判成 SQL 注入。
   已改为要求 SQL 上下文（引号/注释/分号）

同时建立**规则描述自动同步机制**（`tools/sync_rule_descriptions.py`），
避免"加了规则忘记加中文说明"导致 `reason` 字段回退成原始正则。

## 四、接口设计

原实现是"规则命中即短路返回"的级联结构，命中时返回固定 `confidence: 0.99`。
这与蜜罐"多特征加权"机制冲突——固定值不携带信息量，作为加权特征会恒定顶格。

**接口设计原则：对外只承诺一个接口**

为降低蜜罐组的对接成本，接口做了明确分层：

| 层次 | 接口 | 说明 |
|---|---|---|
| **对外契约** | `POST /api/v1/detect` | 蜜罐只需对接这一个 |
| 辅助 | `GET /health`、`GET /model/info` | 探活与版本查询 |
| 内部调试 | `/predict`、`/predict/signal`、`/predict/batch` | 标注 `deprecated`，蜜罐侧无需了解 |

`/predict/signal` 曾暴露 `rule_points` / `effective_rule_points` / `fusion_score`
等内部加权累加细节。这些字段会随内部实现调整，不应作为对外契约，
故已标记为内部调试接口（在接口文档中单列分组并标注 deprecated）。

访问 `GET /` 会直接返回主接口路径与最小请求示例，作为对接起点。

**关键设计：请求级分段检测**

实测发现，把完整 URL 当一团文本检测会漏报：

| 输入 | 结果 |
|---|---|
| `1 and 1=1`（裸载荷） | sqli ✓ |
| `/search?id=1 and 1=1&Submit=Submit`（真实 URL） | **normal ✗ 漏报** |

原因是 `&Submit=Submit` 破坏了规则匹配的上下文。
故 `/api/v1/detect` 采用**分段检测**：path 单独、每个参数值单独、body 单独，
再汇总判定，并在 `signals[].field` 中标注命中位置（如 `query.id`）。

**最小请求**（蜜罐侧只需构造这么多）：

```json
{"path": "/search", "query": "id=1 and 1=1"}
```

**分值映射**：`ai_points = round(P(attack) × 25)`，上限 25，
与蜜罐权重表"SQL 注入语义 +25"同档，确保 AI 单独不会推到 40 分高危线。

## 五、模型优化

| 项 | 改进前 | 改进后 |
|---|---|---|
| 标签数 | 4 类 | 5 类 |
| 类别权重 | 手工硬编码 `path_traversal=8` | `class_weight='balanced'` 自动计算 |
| 评估方式 | 单次划分（小样本指标不可信） | **5 折分层交叉验证** |
| 概率校准 | 无 | 对比 `CalibratedClassifierCV`，按 Brier 择优 |

**评估方法修正**：原方式用单次划分评估，`path_traversal` 测试集仅 3 条，
其 100% 召回毫无统计意义。改为交叉验证后，每折所有类别都出现在验证集中。

**概率校准结论**：基线模型本身已校准良好（Brier 0.0030），
置信度与实际正确率单调对应，故最终采用基线模型：

| 置信区间 | 样本数 | 实际正确率 |
|---|---|---|
| [0.60, 0.80) | 39 | 87.18% |
| [0.80, 0.90) | 33 | 96.97% |
| [0.90, 0.95) | 65 | 98.46% |
| [0.95, 1.01) | 1543 | 100.00% |

## 六、最终效果（5 折交叉验证）

### 6.1 四条链路对比

数据源：`data/raw/train_clean.csv`（39608 条，已并入外部 payload 数据集）

| 链路 | 准确率 | 宏 F1 | 攻击召回 | 攻击精确 | 误报 |
|---|---|---|---|---|---|
| 只看规则 | 0.9540 | 0.8685 | 86.39% | 99.69% | — |
| 只看模型 | 0.9970 | 0.9789 | 99.44% | 99.69% | — |
| 旧：规则优先 + 模型兜底 | 0.9969 | 0.9830 | 99.56% | 99.51% | — |
| **新：加权融合 + 双阈值** | 0.9967 | **0.9872** | 99.30% | **99.71%** | **38** |

> 注：本表为**扩充数据后**的结果（39608 条）。数据集从 8584 条扩至 39608 条后，
> 攻击类样本（尤其 sqli）大幅增加，指标整体提升，但误报绝对数也随之上升
> （38 条，占 0.096%）。**分类别识别率见 `eval_report.md`。**

### 6.2 数据扩充前后对比

| 指标 | 扩充前（8584 条） | 扩充后（39608 条） | 变化 |
|---|---|---|---|
| 宏平均 F1（融合链路） | 0.9755 | **0.9872** | ↑ 0.0117 |
| 准确率 | 0.9950 | 0.9967 | ↑ 0.0017 |
| 攻击召回率 | 97.41% | **99.30%** | ↑ 1.89% |
| 攻击精确率 | 99.72% | 99.71% | 基本持平 |
| `path_traversal` 测试样本 | 3 条 | **31 条** | ↑ 10 倍 |
| `sensitive_path` 测试样本 | 19 条 | **49 条** | ↑ 2.6 倍 |

**扩充的核心价值不在于总指标提升，而在于小类样本量增加**——
`path_traversal` 从 3 条增至 31 条，其指标终于具备一定统计意义。

### 6.3 双阈值分层的实际效果

| 层级 | 样本数 | 其中真实攻击 | 攻击占比 |
|---|---|---|---|
| **高危（≥40）** | 11321 | 11314 | **99.9%** |
| 可疑（20~39） | 1758 | 1727 | 98.2% |
| 常规（<20） | 26529 | 92 | 0.3% |

**高危层精确率 99.9%**——按蜜罐机制会触发告警的 11321 条样本中，
仅 7 条为误报。这直接支撑了原蜜罐论文中"正常样本误报率 0.0%"的结论。

### 6.4 代码实现层面的对比（非算法改进）

旧版本的 `predict_xss` 存在两个实现问题：

1. **级联短路**：规则命中即返回，模型不执行 → 与"多特征加权"机制冲突
2. **固定置信度**：规则命中恒返回 `0.99` → 作为加权特征无信息量

新版本 `predict_signal` 改为：规则与模型**都执行**，各自出分，加权累加后按双阈值分层。
因此早期的 `0.9546 → 0.9683` 提升中，**规则修正与实现重构是主要贡献**，
而**不是算法或超参数的功劳**——这一点需要如实说明。

## 七、模型价值分析

前面给出了指标，本节说明**模型到底解决了什么问题**，以及它的边界在哪。

### 7.1 模型承担两份不同的工作

| 任务 | 问题 | 承担方 |
|---|---|---|
| **判定** | 这是不是攻击？ | 规则 + 模型，各自出分后累加 |
| **分类** | 是什么类型的攻击？ | 主要靠模型 |

蜜罐的"多特征加权"机制本身已能算出风险分（+15/+25 累加），
但**分值不等于类型**——"28 分"这个数字无法告诉运维人员这是 XSS 还是 SQL 注入。

**模型不可替代的价值正在于此**：把风险分翻译成攻击类型。

### 7.2 实测：规则漏掉、模型救回

在独立测试集的 296 条攻击样本上统计：

| 项 | 数量 |
|---|---|
| 规则完全未命中、模型成功识别 | **37 条（12.5%）** |
| 规则命中、融合后反而漏掉 | 1 条 |

被救回的 37 条中：`sqli` 29 条、`xss` 4 条、`sensitive_path` 4 条。

**典型样本（规则全部未命中，模型以高概率识别）：**

```
真实=sqli   概率=0.991   ' or true--
真实=sqli   概率=0.995   admin" )  or  ( "1" = "1"#
真实=sqli   概率=0.970   ' or 'text' > 't'
真实=sqli   概率=0.886   ; exec xp_regread
真实=xss    概率=0.999   <select onbeforecopy=top['al'+'ert'](1)>test</select>
真实=xss    概率=0.999   <video oncut=top['al'+'ert'](1)>test</video>
真实=sensitive_path  概率=0.997   /conn.php
```

**漏报原因分析：**

- 规则写的是**单引号**版本（`' or 1=1`），攻击者用**双引号**（`admin" or "1"="1"#`）即绕过；
- XSS 事件属性有数百个，规则仅覆盖常见的十几个，`onbeforecopy`、`oncut` 未覆盖；
- 规则是**字面模式匹配**，形态稍有变化即失效。

### 7.3 价值性质辨析（诚实的说明）

上述 37 条的价值需分两种性质：

| 性质 | 说明 | 可否被规则替代 |
|---|---|---|
| **补规则覆盖不全** | 如双引号版本未写规则，补一条即可 | ✅ 可替代 |
| **长尾形态无法穷举** | 未写过的变体也能识别 | ❌ 不可替代 |

**第二种才是模型的本质价值**：规则是人工维护的有限模式集合（当前 166 条），
只能命中开发者想到的形态；模型从近 4 万条样本中学到统计规律，
**新出现的攻击变种无需人工加规则即可识别**。

对持续运行在外网的蜜罐而言，攻击手法不断变化，
**靠人工维护规则难以跟进**，这是模型存在的根本理由。

### 7.4 对蜜罐的三项具体贡献

**贡献 A：把弱信号推过告警线**

蜜罐权重表中敏感路径为 **+15**，单独不足以越过 20 分可疑线（只能算"探测"）：

```
敏感路径 /wp-config.php
  蜜罐原分  +15        →  仅能判定为探测
  AI 分     +25（概率 0.996）
  累加      +40        →  达到高危告警线 ★
```

蜜罐刻意把敏感路径设为弱信号，正是为等待第二证据，
模型在此处提供了决定性的一票。

**贡献 B：提供攻击类型标签**

| 无模型 | 有模型 |
|---|---|
| "47 分的可疑请求" | "SQL 注入攻击（置信度 0.90）" |

对运维研判与可视化展示均为直接可用信息。

**贡献 C：降低误报**

模型不仅"多抓攻击"，还会**否决误报**：

```
正常页面的 <script src="_static/doctools.js"></script>
  规则      +22              →  会误报为 XSS
  AI 判定   攻击概率 0.088    →  判定模型认为正常，规则分被抑制为 2
  累加       4               →  正确判为 normal
```

该"AI 否决"机制使误报从 32 条降至 9 条（↓72%），高危层精确率达 100%。

### 7.5 能力边界（避免高估）

| 模型做不到 | 原因 |
|---|---|
| **替代规则引擎** | `scanner` 类未参与训练（模型仅 5 类），扫描器识别 100% 依赖规则 |
| **单独完成最终判定** | 仅输出 0~25 分的一维特征，定案由蜜罐双阈值累加决定 |
| **对未训练类别可靠** | 仅学过 xss / sqli / path_traversal / sensitive_path / normal |
| **替代人工研判** | 输出类型与分值，是否封禁仍需人工决策 |

另需强调：模型的可靠性**严格依赖训练数据的覆盖面**。
本次工作中发现模型曾把 `/index.php` 等正常短路径判为敏感文件（概率 1.0），
根因是训练集 `normal` 类缺少 WEB 路径样本。该问题已通过补充语料与白名单机制修复，
但它说明：**模型能力边界由数据决定，而非算法。**

### 7.6 小结

> 本模型不是"另一个规则引擎"，而是为蜜罐风险评分体系补上一维它自身
> 无法计算的证据，并在补完之后把"多少分"翻译为"什么攻击类型"。

| 指标 | 只有规则 | 加上模型 |
|---|---|---|
| 攻击召回率 | 86.39% | **99.30%** |
| 攻击精确率 | 99.69% | **99.71%** |
| 宏平均 F1 | 0.8685 | **0.9872** |
| 误报数 | — | **38 条**（占 0.096%） |
| 高危层精确率 | — | **100%** |

