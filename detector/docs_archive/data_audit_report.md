## 二、最严重的问题：path_traversal 是"两类东西混在一起"

审计发现，被标为 `path_traversal` 的样本里，**大多数不含任何路径遍历特征**：

```
原始备份 v3 :  69/117 (59.0%) 不含路径遍历特征
训练集      :  32/62  (51.6%)
测试集      :  13/16  (81.2%)   ← 测试集最严重
```

实际的"误标"样本长这样：

```
/admin/          /admin/login     /console       /phpmyadmin/
/pma/            /mysql/          /phpinfo       /Thumbs.db
/swagger-ui.html /swagger-ui/     /CONSOLE       //admin//
```

### 这不是"错误"，而是"两类攻击被合成了一个类"

这两类在语义上完全不同：

| 类别 | 典型样本 | 检测逻辑 |
|---|---|---|
| **真正的路径遍历** | `../../etc/passwd`、`..\..\windows\win.ini`、`%2e%2e%2f` | 找 `../` 序列和编码变形 |
| **敏感路径/目录探测** | `/admin/`、`/phpmyadmin/`、`/swagger-ui.html`、`/Thumbs.db` | 找目录爆破字典、敏感文件名 |

`rules.py` 里的 `path_traversal` 规则（`../`、`/etc/passwd`、`.git/config` 等）**只能命中第一类**。所以第二类样本永远绕过规则、被迫丢给模型，而模型把它判成 `normal`——**从行为上看模型是对的，是标签错了**。

### 建议的处置（三选一）

1. **拆分标签**（推荐）：`path_traversal` 只保留真遍历；新建 `sensitive_path` 类承载 `/admin/`、`/phpmyadmin/`。这更符合你蜜罐的实际语义，也能让 AI 的类型细分更有价值。
2. **合并语义**：把这一类重命名为 `path_access`（路径类访问），并为其单独写规则（目录字典 + 敏感文件名）。
3. **剔除**：如果比赛只认标准攻击类型，把非遍历样本全部剔除出 `path_traversal`。

> ⚠️ 注意：`/swagger-ui.html`、`/Thumbs.db` 这类到底算不算攻击，**取决于你蜜罐的判定策略**。如果是蜜罐故意暴露的诱饵路径，那是攻击；如果是正常接口文档页，就是误标。**这一点需要你确认。**

## 三、sqli 类的噪声来源

### 3.1 碎片样本（数据转换时被截断/误切）

```
测试集里的"sqli"：'UEf'  'UEv'  'UEs'  'v'  '{s'  '( s'  'or'  '/'  '%29'  '||6'
                  '031003000270000'  'tz_offset'
训练集里的"sqli"：'%26'  'left'  '0'  'c'  '//'  'count'  '%21'  '*|'  '%28'  '%7C'  '?'  '@'
```

`UEf`/`UEv`/`UEs` 一眼就是 **base64 分片的残留**；`left`/`count`/`length`/`ord`/`ascii`/`char` 是 **SQL 函数名被单独拆成了一条样本**。这几乎可以断定：`sqli.csv` 在某个环节被按字符/分隔符错误切分过。

### 3.2 来源纯度异常

```
来源 sqli.csv：3935 条  →  sqli=936, normal=2999    ← 76% 被标成 normal
```

一个名为 `sqli.csv` 的数据集，四分之三的样本被转成了 normal，这强烈暗示：
- 原始 CSV 的 `Label` 列映射逻辑有问题（当前代码：非 `"1"`/`"1.0"` 一律当 normal），
- 或该文件本身混入了大量正常语句，且其标签含义不是 0/1。

**需要回看 `sqli.csv` 原始文件的标签取值分布**，而不是简单按 `1 → sqli, else → normal` 映射。

### 3.3 顺带发现

- `data/raw/train_raw_backup_v3.csv` 存在 **`source` 列取值为 `source`、`label` 列取值为 `label` 的脏行**（重复表头），共 1 行。目前靠 `isin(CURRENT_LABELS)` 侥幸过滤掉，建议直接删。
- `source` 列里混入了 `label` 值，说明某次合并操作写错了列。

## 四、数据分布与不均衡

| 数据集 | 总行数 | normal | sqli | xss | path_traversal | normal 占比 |
|---|---|---|---|---|---|---|
| 原始备份 v3 | 8570 | 7013 | 969 | 470 | 117 | 81.8% |
| 训练集 | 4388 | 3590 | 495 | 241 | 62 | 81.8% |
| 独立测试集 | 1098 | 898 | 124 | 60 | 16 | 81.8% |
| **增强集** | 13091 | 3590 | 5883 | 3341 | 277 | **27.4%** |

**关键观察：**

1. 训练集/测试集严格保持 81.8% 的 normal 占比（`train_test_split(stratify=...)` 生效，这点做对了）。
2. 增强集把攻击类放大到 72.6%，**但 normal 一条都没增强**（3590 条原样）。这导致：
   - 训练时模型看到的是 27.4% normal，
   - 测试时面对的是 81.8% normal。
   - **训练/测试分布严重不一致**，模型在真实（normal 占多数）流量上的概率校准会偏。作为蜜罐的"一维加权特征"，这会让分数系统性偏高。
3. **path_traversal 是最大缺口**：原始仅 117 条 → 增强后 277 条，而 sqli 有 5883 条。**相差 21 倍**。你 `train.py` 里硬编码的 `class_weight: path_traversal = 8` 就是在这种极端不平衡下打的补丁。
4. 测试集 path_traversal 只有 **16 条**，其中 13 条还是误标。**真正可用于评估的路径遍历样本可能只有 3 条**——任何指标都毫无统计意义。

## 附：审计方法说明

本报告由 `tools/data_audit.py` 自动生成，逻辑如下：

- **误标检测**：对每条攻击类样本，用该类别的弱特征正则匹配；不含任何特征的即标记为疑似误标。
  - 这会产生少量假阳性（例如高度混淆的 payload），因此**结果是"待复核清单"而非"自动删除依据"**。
- **标签冲突**：按 `text` 分组，检查 `label` 是否唯一。
- **碎片检测**：长度 ≤ 6 或匹配纯 base64 字符集 `[A-Za-z0-9+/=]{1,12}`。
- **跨文件一致性**：求文本集合交集，检测泄漏。

可复核清单见 `suspect_samples.csv`，字段：`dataset`（来源数据集）、`issue`（问题类型）、`label`（原标签）、`text`（样本内容）。
