# 把攻击留在诱饵里

**——网络威胁态势感知与蜜罐诱捕系统**

<!-- SPEECH:BEGIN -->

各位评委老师好。

先看三个动作：试密码、翻文件、扫后台。没有一个是真人，全部发生在我们搭好的诱饵里。这就是我们的项目——网络威胁态势感知与蜜罐诱捕系统。

一句话：用假服务把攻击引进来，用统一事件模型把行为记下来，再用两层 AI 把日志读成结论。

一条命令，拉起 SSH、Web、MySQL、Redis、FTP、Telnet 六类入口和一块态势大屏。六个协议的事件归一成同一条记录：来源、级别、类型、源 IP、会话、标签、载荷。防守方看到的不是六套日志，而是一条时间线。

蜜罐的工作原理，我拆成四个字：骗、隔、记、归。

骗，是仿真真实服务：诱饵账号、像模像样的后台、假文件系统、假数据库键值。攻击者以为找到了入口，其实踩在记录点上。

隔，是 SSH 命令只在内存虚拟文件系统里执行，Web 预览只做校验、不访问目标地址。真实主机和业务数据，始终碰不到。

记，是请求方法、路径、参数、UA、状态码、命令、登录成败全部记录入库。返回 200 还是 404，对我们都是证据。

归，是同一来源一小时内聚成会话，跨协议串成攻击链；再配合限流、爆破封禁、扫描检测和风险评分，把零散行为变成线索。

下面具体看六类入口。

Web 蜜罐是一套企业官网：首页、新闻、产品、解决方案都能正常访问，搜索框、产品参数、文章编号、上传入口都是记录点。/admin 是诱饵后台，不连真实业务。规则覆盖 SQL 注入、XSS、路径遍历、命令执行、SSTI、XXE、SSRF，还准备了虚拟 ERP 和预览接口，让攻击者愿意多待一会儿。

SSH 蜜罐做得更深：whoami、uname、cat /etc/passwd、ls 都有仿真输出，sysinfo 和 appctl 准备了主机人设和服务状态，背后是一套内存虚拟文件系统；未知命令只安全地回 command not found。认证、命令和会话轨迹都有记录。

数据库蜜罐一个进程监听 MySQL 和 Redis：MySQL 完成假握手、假认证、假查询，Redis 回应 INFO、KEYS、GET，给出一组假键值。FTP 做匿名登录、目录列表和文件读取尝试；Telnet 用 D-Link 路由器的横幅和 BusyBox shell 接住探测。

大屏把攻击地图、实时日志、Top IP、会话攻击链、登录审计、系统状态放在一屏，达到阈值还能自动告警。密标给 IP、会话、账号打上密级，记下原因和有效期；调查工作台把同源事件、AI 报告和人工笔记放在一起，结论、证据、状态分开保存；可选配的团队数据中心，还能把多台设备的证据汇到一起。

接下来是我最想讲的部分：AI。我们做了两层：一层是自己训练的攻击识别模型，一层是通用大模型。两层各干各的事，谁也不替谁下结论。

先说自研模型。它不是调用现成的大模型接口，而是我们自己训练、评测出来的，解决请求级判断：一条请求进来，先过规则，再进模型。模型用字符级 TF-IDF 加逻辑回归，覆盖 XSS、SQL 注入、路径遍历、敏感路径和正常五类，扫描器指纹交给规则。训练用了十万条样本，独立测试集准确率 99.36%，宏平均 F1 98.98%；线上用 34 条攻击载荷做端到端实测，检出 27 条，6 条正常请求没有误报，平均延迟 39 毫秒。

它输出 0 到 25 的 AI 加分，和规则分相加，规则分不被覆盖；模型判正常时最终加 0，但仍标记“规则加 AI”，表示它确实看过。模型服务超时或不可达，自动熔断，回退纯规则。它只做分类和加分，不碰主机。

第二层是通用大模型，主要负责四件事：分析、问答、互动、复核。日志里的内容只当数据，不当指令；模型输出必须过格式和证据校验，不合格就重试或降级。

AI 分析，是把零散日志读成攻击过程。后台增量索引事件库和历史归档，每批最多 24 条，挑出最多 6 条代表证据，生成报告：攻击目的、行为推进、风险理由、复核建议、判断局限。关键判断都带原文引用，引用必须逐字出现在原始记录里，编造不出来。报告可以人工复核、加入调查工作台、导出 Markdown。复核意见分为认可、可能误报、可能漏报、待复核，独立保存。它不会说“已经攻破”，因为验证器会拦掉没有证据的成功结论；不能确认，就写不能确认。在完整演练中，81 份报告全部完成，110 次调用成功 108 次。

AI 问答，是围绕日志追问。可以按 IP、关键词检索，最多 250 条候选、24 条相关记录、6 条代表证据；回答带引用，也会明确说“只看到这些片段”。它没有工具、没有联网、没有主机执行权限。

AI 互动，是让蜜罐“会说话”，但只让模型做选择题。SSH 遇到未知命令，模型只能在“命令不存在、服务不可用、拒绝访问”里选；Web 遇到预览请求，只能在“排队、格式错误、服务繁忙”里选。正文由程序模板渲染，状态由程序维护。模型不能生成命令，更不能执行命令。每次交互都留痕，可以在回放页按会话看输入、回应来源和策略。

还有一条异步复核链路：抽样的 HTTP 请求交给大模型二次研判，输出“可疑、未见明确攻击、不确定”三档，必须引用原文；按来源限流、排队，失败不影响规则和响应。规则与 AI 的对照页，把两套判断并排放在一起，谁也不覆盖谁。监控页能看到模型状态、真实调用、失败原因和备用处理，每次调用都有审计；DeepSeek、本地 Ollama、共享网关三种后端可切换。

最后是边界。模型不可用，记录照常、规则照常、诱饵照常；AI 只做辅助，不做裁判。蜜罐的价值，不是抓住每个攻击者，而是让每次探测留下证据；不是替代防护，而是争取时间。

把攻击留在诱饵里，把证据带到屏幕上。谢谢各位评委。

### 5. 口径与答辩提醒

- **指标不是同一次运行**：99.36% / 98.98% 是训练侧独立测试集；27/34、6 条正常、39ms 是 2026-11-07 的模型实测；81/81、110/108 是 2026-10-28 的六协议演练。答辩时不要合并成“同一次实验”。
- **自研模型不是生成式大模型**：它是字符级 TF-IDF + 逻辑回归的分类模型；通用大模型负责分析、问答、互动。两条链路分开讲，反而更清楚。
- **短板要主动承认**：复杂编码混淆仍是弱项，项目 fixtures 二分类准确率 61.5%（见 `reports/model_validation.html`）；可说明规则层兜底、AI 只做加权特征，以及后续数据增强计划。
- **6 条正常请求是小样本**：不要说“零误报率”，说“这批对照里没有误报”。
